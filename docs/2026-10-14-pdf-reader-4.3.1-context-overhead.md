# PDF Reader 4.3.1：Codex 输出核查与上下文开销优化

日期：2026-10-14（Asia/Shanghai）。本阶段实现、原环境安装和验证完成，等待用户验收；不进入 4.4。

## 结论

当前 Codex 环境未复现“Deep 标记已读 47 块、实际仅输出 14 块”的 Core 问题：相同项目 PDF 的 10 批完整 stdout、Codex 工具返回给模型的正文及阅读状态均为同一组 47 块。受控外层截断确实能产生“Core 已完整输出并提交，模型只见截断结果”的差异；原有 `reading-gap` 能撤销计数并恢复重读。因此没有修复或重写批次选择逻辑。

随后完成 4.3.1：新增可选 `--compact` 阅读响应，减少重复元数据和 JSON 空白；全局 Skill 改为按需查询结构与候选，不常规重复发送完整目录。两文档三模式的相同 CLI 流程响应 Token 减少 **26.05%–34.44%**，正文、事件及最终覆盖保持一致。全量 **43 passed in 61.63s**。

## 2. 三层输出与逐批对照

审计脚本每次仅执行一个批次：保存完整子进程 stdout，调用 `reading-status --details` 取得前后快照，将完整 JSON 展示给 Codex，然后才请求下一批。每次精确比较完整输出块 ID、状态新增 ID 和持久化事件的 `full` ID；还检查剩余数和下一待读块。

| 2 | c000006–c000010 | 10 | c000011 |
| 3 | c000011–c000015 | 15 | c000016 |
| 4 | c000016–c000020 | 20 | c000021 |
| 5 | c000021–c000025 | 25 | c000026 |

| 证据层 | 本次正常流程 | 能证明什么 |
|---|---|---|
| Core/CLI 成功输出 | 原始 stdout 的 47 个完整块，与每次提交事件精确一致 | CLI 成功输出内容，不证明模型理解 |
| Codex 工具展示 | 每批预算 4,000 或 3,000 输出 Token；十批均没有外层截断提示 | 这次工具结果完整展示了批次 JSON |
| 模型可见内容 | 十个完整结果逐批进入本对话，每批处理后再继续 | 这次可见 47 块正文，不证明长期保留、理解或视觉核验 |

`c000045–c000051` 是 Deep 初始排除的参考文献，而非跳过后虚标已读。最终 `plan_complete=true`、`complete_text_delivery=false`；仍有 7 块未读。此次核查没有看图，15 个候选回执全部为 0，不据此声称全文视觉验收。

证据目录：`output/reading-4.3.1/codex-audit/`。其中 `normal-batch-*.stdout.json` 为完整 stdout，`*.audit.json` 含完整 before/after 状态及精确 ID 比较；`normal.json` 为任务记录，`normal-source.json` 为文件指纹。`tool-receipts.json` 记录实际工具结果引用，但这些外部声明不是 Core 认证。

## 3. 截断、推进与提交顺序

1. **外层工具截断**：独立 `outer.json` 中 Core 输出并记录首批 5 块；将工具 `max_output_tokens` 限为 100 后，工具报告原结果 1,576 Token，JSON/正文被截断，没有完整可见正文块。此时 Core 仍为 5 块，因为成功 flush 不等于外层完整展示。为该批保守登记 5 个 gap 后计数回到 0，下一块为 `c000001`；正常预算重读后再次为 5，原始 ID 与状态精确一致。
2. **Core 字符截断**：独立 `core-cut.json` 以 20 字符预算返回 `c000001` 的截断预览。`truncated=true`、`needs_full_read=[c000001]`，完整已读数保持 0、剩余计划仍为 47，下一块仍是 `c000001`。
3. **推进机制**：没有独立持久游标；`ReadingTracker.next_batch` 每次从计划内且不在完整已读集合中的块计算待读列表。截断预览不会移出此列表，gap 会将完整块重新放回。
4. **提交顺序**：CLI 先 `print(..., flush=True)`，成功后才 `reading.record`。既有输出失败测试及新增顺序/flush 失败测试通过：输出或 flush 抛出异常不会提交。记录保存失败仍按既有行为报告“内容已输出，但阅读记录未保存”，不可忽略退出码。

没有复现真实 Core 缺陷，因此没有为报告主张强行写修复。新增失败测试针对紧凑输出的新功能：实现前两项测试因不认识 `--compact` 失败，随后通过；不将其描述为复现了 TRAE 的 Bug。

## 4. 最小改动与兼容性

仅修改 CLI 响应、阅读指引及对应测试：

- `reading-start --compact`：保留身份、模式、总块/页、计划数量和策略，省略完整计划 ID 数组。
- `reading-next --compact`：保留顶层文档身份及记录路径；每块完整保留 `id/page_number/section/markdown/truncated/evidence_warnings`，省略重复的块内 `document_id`。剩余数及补读 ID 保留。
- `reading-status --compact`：保留覆盖数值、页覆盖、完成语义、遗漏原因/数量/页码、不完整章节、章节状态计数、视觉计数及信任声明。逐块 ID 和逐项回执按需用 `--details` 查询。
- `--details --compact`：保留全部诊断字段，仅压缩 JSON 空白。不带 `--compact` 时原有响应布局保持不变。
- Skill：普通总结直接开始所选模式；结构不清、排除项异常、缺少块或候选证据时再查 outline/chunks/search。仍逐批实际显示正文，并处理截断与视觉证据。

`reading.py`、BM25、parser、缓存格式、固定启动脚本没有修改。原任务日志和原解析缓存继续可用。同一阅读记录仍只允许一个写入者；不新增确认协议、OCR、API 或环境兼容层。

参考检索/应用/缺项核查记录在 `output/reading-4.3.1/workflow-reference-check.md`，包括更新前冗余调用及更新后截断、候选回执处理。该核查不是自动触发概率或回答质量验收。
