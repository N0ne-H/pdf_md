# PDF Reader 4.3.2.1 Windows 并发 PNG 缓存稳定性修复报告

日期：2026-10-15（Asia/Shanghai）

## 根因与证据

问题是 Windows 发布与缓存读取的文件共享冲突，未发现渲染线程把未写完的临时 PNG 当作完成缓存读取的证据。

- 起点目标测试首次复现：**1 failed in 4.88s**。原 `replace` 出现 WinError 5，随后读取胜出文件时也出现 PermissionError，见 `output/reading-4.3.2.1/pytest-before.txt`。
- 原逻辑关闭临时文件后才发布；但是多个进程先检查缓存不存在，再各自 `replace` 同一路径，晚到者会替换已经发布的完整文件。新增确定性回归在修复前失败，证实胜出文件被替换；同时验证发布前写句柄已关闭、临时数据含 PNG 结束标记且可解码。
- 仅改 Windows 不覆盖重命名还不够：小对照3轮成功，后续10轮仍有2轮缓存命中读取失败，见 `rename-only-stability.json` 和 `rename-only-logs/`。保留这些失败，不将短暂绿灯当作修复完成。
- 第二个确定性测试持有真实 Windows `DELETE` 访问句柄，并允许共享读写。在此条件下，本环境普通 `Path.read_bytes()` 仍因共享契约冲突失败；允许 `FILE_SHARE_DELETE` 的只读句柄能成功。真正独占句柄则仍应失败。读修复前该回归 **1 failed、1 passed**，见 `pytest-sharing-red.txt`。

Windows 共享删除标志允许与其他句柄的删除/重命名访问共存，并不授予调用者删除权限；Python 文档也明确 Windows rename 在目标已存在时失败，而 replace 可覆盖目标。采用这两个已验证的 API 语义处理竞争，不猜测杀毒软件或 ACL 是根因。[Microsoft CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)、[Python os.rename](https://docs.python.org/3.11/library/os.html#os.rename)。

## 实际修改

业务代码仅修改 `src/pdf_reader/render.py`：

1. Windows 使用 `temporary.rename(output)` 发布完整文件，已有胜出文件时校验并复用；其他平台保留原 replace 路径。目录和文件名不变。
2. 两个缓存读取位置共用 `_read_png`：Windows 以 `GENERIC_READ`、共享读/写/删除、`OPEN_EXISTING` 打开，再将句柄交给标准二进制流读取和关闭；其他平台仍使用 read_bytes。无新依赖，无重试或等待。
3. 原有错误传播、PNG 解码、竞争胜出文件尺寸检查和 finally 临时文件清理保留。不绕过访问权限，不将无效 PNG 或独占锁伪装为缓存命中。

`tests/test_runtime.py` 新增7个参数展开后的回归，保留原目标测试；将原发布故障注入点适配到当前平台实际使用的方法。新增用例覆盖晚到者保留胜出文件、真实共享句柄/独占锁、损坏与截断缓存、持续访问拒绝及发布前文件关闭。Windows 专用测试在本机全部执行，没有跳过。

另新增本报告和实施计划，并更新 PROJECT_STATE.md；本地诊断脚本和日志在 `output/reading-4.3.2.1/`，按原项目规则被 Git 忽略。阅读策略、BM25、Compact、解析、文档缓存格式及全局 Skill 路由保持原样。
